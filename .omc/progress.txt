## PH2-G1 — implemented (2026-04-27)
- Tool-call format compliance gate. New file:
  tests/spike/test_openrouter_tool_calling.py + tests/spike/__init__.py.
  4 live-API test cases against OpenRouter + Gemini Flash Lite Preview:
  * test_g1_single_bash_tool_call — model emits one well-formed
    bash tool_call with parseable JSON args containing 'command' that
    references uptime.
  * test_g1_single_read_tool_call — bash analogue for the read tool;
    args dict contains 'path' = '/etc/hostname'.
  * test_g1_single_web_search_tool_call — same shape check for
    web_search; args contains non-empty 'query'.
  * test_g1_multi_step_tool_chain — two-turn conversation. First turn
    issues bash(uptime). Synthetic uptime result fed back as a `tool`
    role message containing a unique sentinel ('0.4242'). Explicit user
    follow-up tells the model to echo only the 1-minute load average
    from the prior tool result without re-running uptime. Second
    LLM turn must produce a bash tool_call whose `command` literal
    contains the sentinel — proves the second call is grounded on
    the first call's tool result, not a fresh derivation.
- Initial run with the PRD-suggested model `google/gemini-flash-1.5`
  returned `404 No endpoints found` from OpenRouter. Switched the test
  default to the same model the project already uses
  (`google/gemini-3.1-flash-lite-preview-20260303`); `PH2_GATE_MODEL`
  env var overrides for ad-hoc reruns.
- Initial multi-step prompt let the model choose to re-run
  `uptime | awk ... | xargs` instead of using the fed-in tool result.
  Hardened the test by adding an explicit user turn after the tool
  result that forbids re-running uptime, and by replacing the
  free-form load-average assertion with a unique sentinel match.
- Module-level skipif guards on `OPENROUTER_API_KEY` so this gate
  stays a no-op in CI without the secret.
- Verification: `uv run pytest tests/spike/test_openrouter_tool_calling.py
  -q` → 4 passed in 5.37s.
- Acceptance criteria from PRD PH2-G1: all 8 ACs verified.
  Halt-condition not triggered — gate PASSED.
- Learning: the project's openrouter_model is a preview model with a
  date-stamped suffix; PRD model strings should be checked against
  src/config.py before assuming OpenRouter accepts them.
- Learning: live-LLM tests need explicit anti-rerun instructions plus
  unique sentinel assertions to verify grounding-on-tool-result; a
  free-form "echoes the value" assertion is too lenient because the
  model will happily re-derive the value from a fresh tool call.

## PH2-03 — partial (2026-04-27): tool registration done, LLM-side ACs blocked on PH2-02
- New file: src/llm_tools.py — Pipecat ``register_function`` bridge
  that maps every enabled tool in src/tool_registry.py (13 tools:
  bash, read, write, edit, web_fetch, web_search, workflow,
  re_enroll, list_profiles, create_profile, delete_profile,
  rename_profile, cancel) to a Pipecat ``FunctionSchema`` AND an
  async ``FunctionCallParams`` handler. Public API:
  * ``build_tools_schema()`` — returns
    ``ToolsSchema(standard_tools=[FunctionSchema, ...])`` for the
    LLMContext (consumed by PH2-02).
  * ``register_all_tools(llm, *, settings=None)`` — calls
    ``llm.register_function(name, handler, cancel_on_interruption)``
    for every enabled tool. Returns the list of names actually
    registered for assertions.
- Per-tool spec table ``_TOOL_SPECS`` carries three columns:
  ``properties`` (OpenAI-style parameter dict), ``required`` (list
  of required parameter names), and a ``serializer`` that folds the
  LLM's structured ``arguments`` dict back into the string ``args``
  the legacy ``execute_direct`` API expects (e.g. write expects
  ``"path: content"``). This split lets the LLM see typed schemas
  while keeping ``direct_tools.py`` untouched.
- Handler factory ``_make_handler`` wraps each tool:
  * Pulls structured args off ``params.arguments``, runs them
    through the per-tool serializer, calls
    ``await execute_direct(tool, args_str, settings)``.
  * Propagates ``asyncio.CancelledError`` so Pipecat's runner sees
    the cancel — the bash kill paths (``os.killpg`` with SIGTERM/
    SIGKILL escalation) live inside ``_execute_bash`` already
    (CCS-05b), so the handler relying on that surface is the right
    architectural choice (duplicating os.killpg in the handler
    would risk double-kill).
  * Catches everything else and surfaces a structured failure dict
    (``success=False``, ``error=<msg>``) via ``result_callback`` —
    pipecat must never see a raised exception except cancellation.
- The ``cancel`` tool registers with ``cancel_on_interruption=False``
  because PH2-05 routes real cancels through ``InterruptionFrame``;
  the LLM-side ``cancel`` handler is a tool-surface placeholder so
  the model sees a parsable function name. All other tools register
  with ``cancel_on_interruption=True``.
- Tests added: tests/test_llm_tools.py — 8 tests:
  * Schema covers every enabled tool name (no drift between
    registry and llm_tools).
  * Schema captures properties + required for representative tools
    (bash, write, list_profiles).
  * register_all_tools registers every enabled tool.
  * cancel_on_interruption flag is False for cancel, True for bash
    (regression guard for PH2-05's contract).
  * Handler dispatch end-to-end: bash tool_call -> execute_direct
    -> result_callback (this is PRD AC8 for PH2-03 — "tool call from
    LLM executes and result callback fires").
  * write serializer folds structured args into "path: content"
    correctly.
  * Handler exception path returns failure dict via
    result_callback (does NOT raise into pipecat).
  * Handler cancellation propagates CancelledError up to pipecat.
- Verification:
  * `uv run pytest tests/test_llm_tools.py -q` → 8 passed in 0.14s.
  * `uv run ruff check src/llm_tools.py tests/test_llm_tools.py` →
    all checks passed.
  * Full suite (excl spike): `uv run pytest -q --ignore=tests/spike`
    → 908 passed, 16 skipped (= 900 baseline + 8 new = zero
    regressions).
- Acceptance criteria status (PRD PH2-03, 9 ACs):
  * AC1 (tool_registry reads all 13 tools) — DONE (registry
    untouched; llm_tools consumes get_enabled_tools).
  * AC2 (async handler per tool wrapping _execute_*) — DONE.
  * AC3 (handler calls await result_callback on success) — DONE.
  * AC4 (CancelledError handled, os.killpg for bash) — DONE via
    propagation to _execute_bash where the kill lives.
  * AC5 (llm.register_function called for all 13 tools) — DONE.
  * AC6 (ToolsSchema with FunctionSchema per tool) — DONE.
  * AC7 (LLMContext created with tools=...) — BLOCKED on PH2-02.
  * AC8 (integration test: tool call -> execute -> callback) — DONE.
  * AC9 (grep IntentQueue/intent_parser/IntentStreamParser in

## Iteration 16 — architect review fixes (2026-04-27)

Architect verification (oh-my-claudecode:architect) flagged two HIGH
regressions and several lower-severity items. Both HIGHs are now
fixed and covered by new tests; LOW/MEDIUM items deferred per the
architect's own "approved with punch list" verdict.

### HIGH 1 — Action log was never populated post-cutover
- **Root cause**: Old ``generator.py`` called
  ``conversation_manager.record_action_pending`` and ``actions.py``
  called the matching ``record_action_result`` /
  ``record_action_cancelled`` / ``record_action_error``. Both modules
  were deleted. The new ``llm_tools.py`` handler only called
  ``execute_direct``; the action log was permanently empty,
  ``ContextBuilder._format_recent_actions`` rendered ``"(none)"``,
  and the LLM lost the CCS-02 / CCS-04 grounding cues that prevent
  duplicate web searches.
- **Fix**: ``src/llm_tools.py`` — ``register_all_tools`` now accepts
  an optional ``conversation_manager``. ``_make_handler`` brackets
  every invocation with ``record_action_pending`` (before
  ``execute_direct``), then ``record_action_result`` (with extracted
  ``summary`` + structured ``items`` for web_search), or
  ``record_action_cancelled`` on ``CancelledError``, or
  ``record_action_error`` on any other exception. Synthetic
  ``intent_id`` from ``itertools.count()`` keeps the deque entries
  matchable across pending → done transitions. Each record call is
  try/except'd so a misbehaving conversation manager cannot break
  the tool surface.
- ``src/pipeline.py`` — ``register_all_tools(...)`` call site updated
  to thread the ``conversation_manager`` (which ``build_pipeline``
  already accepts).
- New tests in ``tests/test_llm_tools.py``: 4 tests covering
  pending+result, error path, cancel path, and backwards-compat
  no-op when ``conversation_manager=None``.

### HIGH 2 — MCP server descriptions dropped from system prompt
- **Root cause**: Old ``generator.py`` computed
  ``_mcp_descriptions`` at init and injected them as
  ``ctx["mcp_servers"]``. ``ContextBuilder.build_for_generator``
  never set the key; ``llm_context_injector.py`` reads
  ``context.get("mcp_servers")`` (line 119) but it was always
  ``None``. If users had MCP servers in
  ``workspace/.mcp.json`` the LLM didn't know any
  ``mcp__<server>__*`` tools were callable.
- **Fix**: ``src/context.py:ContextBuilder.__init__`` now reads
  ``workspace_dir/.mcp.json`` once at startup via
  ``mcp_utils.read_mcp_servers`` + ``build_mcp_prompt_block`` and
  caches the result on ``self._mcp_descriptions``.
  ``build_for_generator`` injects it into the result dict as
  ``mcp_servers`` when non-empty (key is omitted when no servers
  exist so the system-prompt block stays clean on cold setups).
- Adjusted ``tests/test_context.py:test_build_for_generator_returns_minimal_keys``
  — required-key assertion is now a subset check (mcp_servers is an
  optional addition). Two new tests cover the populated-servers and
  no-servers paths against a tmp .mcp.json.

### MEDIUM / LOW — deferred (per architect punch list)
- ``ConversationManager.update_summary`` is no longer called by
  anything in the active pipeline. Conversation summary stays empty
  in the DB. The LLMContext aggregator already preserves prior turns
  in-memory, so multi-turn grounding still works at the LLM level —
  only the stored summary projection is dead. Removing
  ``update_summary`` (and the entity/topic-tracker it feeds) is a
  larger refactor and is left for a follow-up cleanup pass.
- ``ConversationManager.extract_topics`` is a noop with zero callers
  (legitimately dead code, but harmless). Will be deleted in the
  same cleanup pass.
- Stale config fields (``intent_queue_max_pending``,
  ``topic_extraction_*``, ``DeciderState`` enum, etc.) — left in
  place; ``tests/test_config.py`` asserts their default values, so
  removing them churns config tests for zero behavioural gain. Same
  cleanup pass.
