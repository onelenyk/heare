### Design decisions
1. UPSERT keying on intent_id required a UNIQUE index. Partial indexes (... WHERE intent_id IS NOT NULL) are NOT supported by SQLite ON CONFLICT — verified with sqlite3.OperationalError "ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint". Solution: unconditional UNIQUE INDEX on intent_id; SQLite treats multiple NULLs as distinct so legacy log_action() rows still coexist.
2. The original actions.decision_id was declared NOT NULL with FK to decisions(id). Action_log entries are keyed by intent_id and have no decision_id. Solution: a one-shot table rebuild migration in _migrate_action_log_columns when a NOT NULL constraint is detected via PRAGMA table_info. PRAGMA foreign_keys=OFF wraps the rebuild per SQLite docs §7.11.
3. Persistence is fire-and-forget via asyncio.create_task with a guarded try/except. In-memory mutation happens FIRST so reads stay coherent within a turn even if the DB is slow/locked. Sync-test path with no running loop is detected via asyncio.get_running_loop() RuntimeError → silent skip.
4. Hydration reverses the newest-first SELECT result so the deque appends chronologically (oldest at left, newest at right) — matches how new entries arrive at runtime.
5. result_json is a JSON dict {summary} or {error}, leaving room for Story 2 to extend with {summary, items}.

### Gotchas
- Old DBs created with the v2/v3 schema have decision_id NOT NULL — migration must handle the rebuild path. New DBs get the nullable decision_id directly from SCHEMA.
- The test_indication.py::test_notify_dispatches_to_all_enabled_backends pre-existing time-of-day flake is unaffected by this story — does not touch indication or quiet-hours.

### Design decisions
1. Knowledge-graph at n=0 with kind="answer_box" rather than fragmenting to a separate field. Output rendering keeps the 📚 prefix; items rendering uses the n=0 slot. Documented in the _search_serper docstring; covered by test_serper_knowledge_graph_at_position_0.
2. WEB_TAIL_LIMIT lives as a function-local constant inside _format_recent_actions (the previous tail_limit was inline-literal). Both the constant and the AC use 1800 — single source of truth.
3. Tail-first truncation drops whole blocks (not character-level mid-block cuts) so that surviving items remain syntactically intact "1. …\n…\n…" entries the LLM can address by ordinal. Pathological case of single-block-too-long still character-truncates with a "(N more items truncated)" tag — unlikely in practice but covered defensively.
4. record_action_result keeps items optional (default None) for backward compatibility. Callers that pass only summary produce result_json={"summary": …} as before. Story 1's hydrate path was extended to read parsed["items"] only when it's a list — preserves resilience to malformed JSON.
5. The fallback path comment in _format_recent_actions explicitly references tests/test_context.py:391-440 so future maintainers know the legacy rendering must stay byte-compatible for entries without items (consensus-review condition #3).

### Gotchas
- Old in-memory entries with no items key fall through to the legacy result blob render. This is by design — legacy DB rows hydrated without items still render via result_json["summary"], no surprise breakage.
- Serper organic items start at n=1 even when the knowledge_graph sits at n=0 — n is contiguous within the organic list (1..5). Test asserts this explicitly.
- The tests/test_indication.py::test_notify_dispatches_to_all_enabled_backends pre-existing time-of-day flake remains the only failing test in the full suite (current run was at 01:01 local, inside the documented 22:00–07:00 quiet-hours window).
