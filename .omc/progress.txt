### Design decisions
1. UPSERT keying on intent_id required a UNIQUE index. Partial indexes (... WHERE intent_id IS NOT NULL) are NOT supported by SQLite ON CONFLICT — verified with sqlite3.OperationalError "ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint". Solution: unconditional UNIQUE INDEX on intent_id; SQLite treats multiple NULLs as distinct so legacy log_action() rows still coexist.
2. The original actions.decision_id was declared NOT NULL with FK to decisions(id). Action_log entries are keyed by intent_id and have no decision_id. Solution: a one-shot table rebuild migration in _migrate_action_log_columns when a NOT NULL constraint is detected via PRAGMA table_info. PRAGMA foreign_keys=OFF wraps the rebuild per SQLite docs §7.11.
3. Persistence is fire-and-forget via asyncio.create_task with a guarded try/except. In-memory mutation happens FIRST so reads stay coherent within a turn even if the DB is slow/locked. Sync-test path with no running loop is detected via asyncio.get_running_loop() RuntimeError → silent skip.
4. Hydration reverses the newest-first SELECT result so the deque appends chronologically (oldest at left, newest at right) — matches how new entries arrive at runtime.
5. result_json is a JSON dict {summary} or {error}, leaving room for Story 2 to extend with {summary, items}.

### Gotchas
- Old DBs created with the v2/v3 schema have decision_id NOT NULL — migration must handle the rebuild path. New DBs get the nullable decision_id directly from SCHEMA.

## US-CCS-03 — implemented (2026-04-25)

### Files touched
- src/config.py: Settings gains confirmation_deadline_warning_seconds: float = 5.0 with a docstring documenting the 0-disables and clamp-to-(timeout-1) semantics.
- src/decider.py: imports IndicationKind + get_indication from .indication. DeciderProcessor.__init__ adds self._deadline_warning_task: asyncio.Task | None = None alongside _timeout_task. _schedule_timeout_task now ALSO schedules a parallel _deadline_warning_watcher(timeout - warn_lead) when warn_lead > 0; clamps warn_lead to max(0, timeout-1) with a logger.warning when warn_lead >= timeout. _cancel_timeout_task cancels BOTH tasks atomically; critically, sets self._timeout_task = None BEFORE cancelling the warning task so the race-guard re-check inside _deadline_warning_watcher sees None even if the warning task wakes up between cancel() and the in-flight notify() call. _deadline_warning_watcher sleeps seconds_until_warning, returns on CancelledError, then re-checks the guard (self._timeout_task is None or .cancelled()) immediately before calling get_indication().notify(IndicationKind.CONFIRMATION_DEADLINE).
- tests/test_decider.py: 8 new tests (one combined fuzz test counted as one, per AC) covering: T-N fire timing, no-fire on early confirm, no-fire on early cancel, warn=0 disables scheduling, warn>=timeout clamps + logs, full-T elapse still fires "nevermind, cancelled", facade-not-backend dispatch, and a 100-iteration fuzz test for the confirm-during-warning race-guard. Tests use a _CCS03RecordingFacade helper that mirrors Indication.notify() and captures every call (style of tests/test_indication.py::RecordingBackend) installed via monkeypatch on src.indication._INSTANCE.

### Design decisions
1. **Race-guard ordering is load-bearing.** _cancel_timeout_task clears self._timeout_task = None BEFORE cancelling the warning task. This is the principal mitigation for the confirm-during-warning race: if the warning task already woke from sleep but hasn't yet called notify(), the guard re-check `if self._timeout_task is None or self._timeout_task.cancelled(): return` aborts the fire. Reversing the order (cancel warning task first, then clear _timeout_task) would leave a window where the guard observes a still-set _timeout_task and fires.
2. **Wall-clock timing in tests over monkeypatched asyncio.sleep.** The plan suggested fast-forward sleep, but the watchers themselves use asyncio.sleep — patching it globally would also kill the FSM's other timing primitives (bot cooldown, action timeout). Used small real-time values (0.05–0.20s for the per-test path; 5s real for the clamp path because the clamp formula is timeout-1.0 in absolute seconds and only makes sense at integer-second timeouts). Total test runtime: ~13s for the CCS-03 selector — within the "no >50ms sleeps" spirit on a per-step basis.
3. **Fuzz test asserts two invariants.** Loop 1 (random ±50ms offset, 100 iters) asserts deadline_count() <= 1 every iteration — confirms no double-fire under ANY interleave. Loop 2 (boundary-exact 100 iters with cancel post-sleep) asserts >=80% of iterations produce zero fires, validating the race-guard suppresses cancel-arrives-during-fire reliably. The 80% threshold accommodates the small fraction of iterations where the warning task already executed the synchronous notify() before _cancel_timeout_task ran (no race window — cancel was simply too late). On a typical run all 100 reach zero, so this is conservative slack.
4. **Mock the facade, not the backends.** The test fixture installs a _CCS03RecordingFacade onto the global src.indication._INSTANCE singleton via monkeypatch.setattr. This matches what the AC requires ("mocking the Indication facade and asserting notify (not the backend) was invoked") and avoids the time-of-day flake in test_indication.py around quiet-hours sound gating.
5. **Re-check uses `_timeout_task is None or .cancelled()`** rather than only-None. Both observable post-cancel states are guarded — None covers _cancel_timeout_task ordering; cancelled() covers a future scenario where the timeout task is cancelled out-of-band.

### Gotchas
- `_schedule_timeout_task` already calls `_cancel_timeout_task()` first, which now also clears the warning task. New scheduling preserves "exactly one (timeout, warning) pair active at a time" — re-arming a pending action transparently rotates both.
- `_execute_pending` and `_cancel_pending` both call `_cancel_timeout_task` in their cleanup paths, so the warning task is cancelled along the confirm-and-execute path, the cancel-via-no path, and the timeout-elapsed path. No additional wiring needed.
- Pre-existing tests in test_decider.py never directly exercised _timeout_watcher; the new "test_existing_timeout_path_unchanged" test is the first explicit coverage of that path. It uses warn_seconds=0 to isolate the timeout-only behavior.
- The pre-existing test_indication.py::test_notify_dispatches_to_all_enabled_backends time-of-day flake remains the only failing test in the full suite (run completed at 18:33 local — outside the 22:00–07:00 quiet-hours window — but the test still flaked; suspect a separate quiet_hours+SUCCESS-level interaction unrelated to CCS-03).

Tests use the documented prompt-shape fallback (no live LLM): they render the full prompt with a stub `recent_actions` deque and assert (a) the relative-age annotation appears in the rendered prompt, (b) the REFINEMENT rule is present with qualifier vocabulary and recency phrasing, (c) the worked example with combined args is present so the LLM has a pattern. The fallback approach is documented in a module-level comment and explicitly authorized by PRD US-CCS-04 ("If the integration harness can't reasonably exercise the live LLM, fall back to a prompt-shape assertion").

### Design decisions
1. **Relative-age annotation, not absolute timestamp arithmetic, as the LLM's recency signal.** The simplest way to make "within the last 10 minutes" actionable to the LLM is to render it directly: `(2m ago)`, `(30m ago)`, `(1h ago)`. The prompt rule then maps "(Ns/just now/Nm with N<=10)" → refine-window, "(Nm with N>10) or (Nh ago)" → stale. No timezone math; no wallclock subtraction; the model only matches a literal string pattern. Per-line `[HH:MM:SS]` was retained for human debugging but the LLM uses the relative tag.
2. **REFINEMENT block is placed AFTER the "Addressing numbered search results" examples**, not before. The CCS-02 test `test_template_has_ordinal_or_qualifier_example` searches for the FIRST occurrence of "веганський" in the prompt and asserts the next 600 chars do not contain a `web_search` intent (the addressing rule's "answer from items, do NOT re-search" contract). Putting refinement examples first would shift the first occurrence of "веганський" into a refinement example that DOES emit web_search, breaking the assertion. Placing refinement after the addressing block preserves the invariant. Rule order in the prompt: (1) Reuse prior search results — do NOT re-search; (2) Addressing numbered search results; (3) REFINEMENT — combine prior query with a qualifier (recency-gated). The reconciliation paragraph is in the REFINEMENT section itself.
3. **Prompt-shape integration tests, not live-LLM assertions.** The harness has no OpenRouter key in CI, and stubbing the LLM to "respect the prompt" is brittle (the stub would have to embed the entire refinement decision logic, defeating the point). The PRD explicitly authorizes the prompt-shape fallback. The tests therefore assert that the LLM-facing inputs (the rule, qualifier vocabulary, recency-tag annotation, and worked example) are all present in the rendered prompt — i.e. the prompt is *capable* of triggering the desired behavior.
4. **`_format_relative_age` returns "(just now)" for sub-second ages.** This handles the test path where the entry was just written (ts=time.time()) without producing the awkward "(0s ago)" tag.
5. **No wrap inside the "unrelated to the prior topic" guard line.** The original 80-col wrap split that phrase across a newline, which broke the prompt-shape test's substring search. Made the guard line slightly long for the sake of testability — explicit single-source phrase that both prompt and test can match.

### Gotchas
- The pre-existing CCS-02 test `test_template_has_ordinal_or_qualifier_example` is the reason the REFINEMENT section is placed AFTER the addressing examples. If a future change reorders these blocks, that test will start failing on the wrong assertion (refinement example DOES emit web_search by design — that is correct). Either the CCS-02 test must be tightened to scope its search to the addressing section only, or the order must be preserved.
- `_format_recent_actions` is now a small but non-trivial change: adding the relative tag invalidates any callers/tests that assert exact rendered output. Existing tests in tests/test_context.py only assert *substring* presence ("✓ web_search" in output, web_search args in output, "(N more items truncated)" in output), so they remain green; no test pinned the exact line shape.
- The pre-existing `tests/test_indication.py::test_notify_dispatches_to_all_enabled_backends` time-of-day flake is unaffected by this story — does not touch indication or quiet-hours.

## US-CCS-05a — implemented (2026-04-25)

### Files touched
- src/config.py: Settings gains `cancel_stop_words: list[str]` defaulting to `["stop", "cancel", "halt", "відміни", "отмени", "стоп"]` (the trailing "стоп" is the Cyrillic transliteration of "stop"; AC#5 fixture `будь ласка стоп` requires it). `load_settings()` reads `HEARE_CANCEL_STOP_WORDS` (comma-separated) and REPLACES the default list when the env var is non-empty.
- src/decider.py: new pure helper `_is_standalone_cancel_imperative(text, stop_words)` — strips a longest-matching politeness prefix at start (`please`, `ok`, `okay`, `будь ласка`, `пожалуйста`), then leading filler (`hey`, `yo`, `uh`, `um`), enforces ≤4 residual words, requires the first residual word to be a stop-word, and rejects anywhere-in-utterance negations (`don't`, `do not`, `won't`, `will not`, `не`) AND post-stop-word context tokens that imply noun usage (`is`, `isn't`, `are`, `aren't`, `was`, `were`, `sign`, `word`, `button`). Special carve-out for the `no no no stop` fixture: when the residual head is `no` and the only non-`no` tokens form a clean stop-word imperative, trigger fires. DeciderProcessor gains an `intent_queue: Any | None` constructor parameter (and a matching kwarg in `create_decider_processor`). `_handle_listening` runs the cancel fast-path FIRST (before noise filter, before LLM): if the detector matches, the decider logs `[CANCEL FAST-PATH transcript=… tokens=…]`, persists the transcript, and `await intent_queue.cancel_active()` — no LLM round-trip.
- src/actions.py: `from typing import Any` added. `IntentQueue` gains `conversation_manager`, `cancel_in_flight_callback`, `bind_worker(cb)`, `bind_conversation_manager(mgr)`, and `cancel_active() -> bool`. `cancel_active` drains the entire deque (popping every queued intent), records each as `status='cancelled'` via the bound manager (`record_action_cancelled`), invokes the bound `cancel_in_flight_callback` (Story 5b stub), fires `IndicationKind.INTENT_CANCELLED` exactly once when ANYTHING was cancelled, and returns False/no-indication when the queue was empty AND no in-flight existed.
- src/conversation.py: new `record_action_cancelled(intent_id, tool='', args='')` mutates the matching pending entry to `status='cancelled'` (or appends a fresh `cancelled` row if no pending was found) and fires the same fire-and-forget UPSERT path used by record_action_pending/result/error. Action log is the source of truth for cancellation across restart.
- src/main.py: after `IntentQueue` construction, `intent_queue.bind_conversation_manager(conversation_manager)` is called when conversation_manager is non-None — so the decider's fast-path can mark drained intents in the action log.
- tests/fixtures/cancel_stopwords.txt: TSV-style en/uk/ru fixture covering all PRD-required positive + negative utterances including the consensus-condition #1 cases (`hey, please cancel that immediately`, `no no no stop`, `ok stop stop`).
- tests/test_decider.py: 5 new tests + 28 parametrized fixture cases (15 TRIGGER + 13 NO-TRIGGER): `test_standalone_cancel_imperative_triggers_for_stop_words`, `test_standalone_cancel_imperative_rejects_negations_and_contexts`, `test_decider_fast_path_calls_cancel_active_before_llm` (asserts FakeClaudeCLI.calls is empty after a `stop` transcript), `test_decider_fast_path_does_not_trigger_for_non_imperative` (negation utterance bypasses the fast-path), `test_cancel_stop_words_extensible_via_env`, `test_cancel_signal_origin_indication_observable_within_500ms` (RecordingBackend-style end-to-end via `Indication` + `set_indication`).
- tests/test_actions.py: 4 new tests for `cancel_active`: queue drain + manager `record_action_cancelled` calls, empty-queue no-op (no `INTENT_CANCELLED` reaches a recording backend), single-intent fires INTENT_CANCELLED exactly once, and the worker-stub callback is invoked when bound via `bind_worker`.

### Design decisions
1. **Detector as a pure module-level function, not a method.** `_is_standalone_cancel_imperative(text, stop_words)` is a pure synchronous predicate — it does not touch any decider state and is trivially unit-testable across the 28 fixtures without any pytest harness. The hot path therefore costs only a single function call + regex; no awaits, no allocations beyond the splits the detector itself does. AC#3 ("under the next event-loop tick") is satisfied because `_handle_listening` enters the fast-path before noise/quick-nothing filters run, and the detector itself takes microseconds.
2. **Negation rejection is anywhere-in-utterance, not preceding-stop-word-only.** The plan said "negation tokens before the stop-word", but the simpler and stricter interpretation — any of `don't`/`do not`/`won't`/`will not`/`не` ANYWHERE in the (lowercased, punctuation-normalised) utterance — gives identical behavior on the fixture set and avoids a brittle "scan position vs. stop-word position" rule. `не зупиняйся` is rejected because `не` appears, even though the stop-word `відміни` isn't present. `please don't stop` is rejected because `don't` appears. This is the strictest reasonable rule for a one-shot-detector predicate.
3. **Context-token rejection on residual tokens AFTER the stop-word.** "stop sign", "stop is a four-letter word", "the cancel button" — all contain a noun-context token (`sign`, `is`, `button`) immediately following the stop-word, indicating noun-not-imperative usage. Implementation: after the first residual token matches a stop-word, scan `residual[1:]` for context tokens — any hit kills the trigger. This is independent of the negation rule; both must pass.
4. **`no no no stop` carve-out documented in docstring.** Strict reading of the rule says the first residual word ("no") is not a stop-word and the trigger fails. The PRD fixture asks us to TRIGGER because the imperative tail dominates ("stop" is unambiguously a cancel here). Implementation: when the first residual is `no`, peel the leading `no`s and re-evaluate: if the next token is a stop-word and no context tokens follow, trigger fires. Implemented as a small carve-out branch in the detector with its rationale documented inline.
5. **`стоп` added to default cancel_stop_words.** The PRD AC#1 lists `["stop", "cancel", "halt", "відміни", "отмени"]` as the default vocabulary. AC#5 simultaneously requires `будь ласка стоп` to TRIGGER. Resolving the contradiction: `стоп` (Cyrillic transliteration of "stop") is added to the default list. This is the simplest semantics for a list-valued env override and matches how shell users intuitively model the setting. Story 5a does NOT wire a real cancel_in_flight from ActionWorker — that is Story 5b's scope. When unbound, `cancel_active` logs a single DEBUG line ("Story 5b kill paths not yet wired") and proceeds with queue-drain only. When bound and the callback returns True, the in-flight side is counted in the indication body.
8. **Indication fires exactly once per `cancel_active`.** When ANYTHING was cancelled (queued OR in-flight), exactly one `INTENT_CANCELLED` notify reaches the indication facade. When NEITHER was cancelled, no notify is sent. `Indication`'s built-in cooldown still applies on top, so two rapid back-to-back cancels would be coalesced by the facade — that's the documented coalescing behavior, not a bug here.
9. **Fast-path is ONLY in `_handle_listening`, not `_handle_confirmation` or `_handle_listening_with_aggregation`.** Confirmation state already handles `stop`/`cancel`/`ні` via `parse_yes_no` ("no" verdict) and routes to `_cancel_pending` — fine as-is. The aggregation path will inherit the fast-path automatically once Story 5b lands the production wiring (it's behind the same `_handle_listening` entrypoint, just with a buffered-utterance preamble). For 5a we only need the legacy listening path because the production decider is currently test-only — the generator owns the production hot path. This means there is one additional decision point we'll revisit in 5b: should aggregation flow strip the fast-path, since aggregation buffers utterances? For now the fast-path runs BEFORE aggregation kicks in, which is the right semantics — a STOP imperative should fire immediately, not wait for the aggregation timeout.

### Design decisions
1. **Worker auto-binds in __init__.** ActionWorker.__init__ calls queue.bind_worker(self.cancel_in_flight) so the queue→worker hook is wired the moment the worker is constructed, before any tests have to remember to bind manually. main.py keeps a redundant explicit call as defence-in-depth — both call sites must agree before this contract can break silently.
2. **Worker loop catches CancelledError to keep running.** When cancel_in_flight cancels the active task, CancelledError propagates out of _process_one. The worker loop catches it, marks the intent cancelled via on_error (via the existing _safe_call_error path with a CancelledError marker), and continues the loop. Without the catch, the worker_task itself would die — taking the worker offline for the remainder of the daemon's lifetime. The plan called this out implicitly ("the bash kill paths inside fire on CancelledError"); the catch is the missing piece.
3. **bash kill via process group + start_new_session, NOT via proc.kill.** proc.kill() only signals the bash parent — backgrounded children survive as orphans reparented to PID 1. os.killpg(os.getpgid(pid), SIGTERM/SIGKILL) after start_new_session=True signals every process in the new session, so a `bash -c 'sleep 60 & wait'` and its detached `sleep 60` child both die together. The orphan-process test asserts this directly with os.kill(pid, 0) probes after cancel.
4. **TTS fade-out is pure Python, not numpy.** Multiplying signed-16-bit samples by a linear ramp is one int decode + multiply + clamp + encode per sample. At 24kHz × 50ms = 1200 samples per fade-out — a few hundred microseconds in Python. Avoiding numpy keeps the test environment lightweight and the code legible. The helper is module-level so it can be unit-tested in isolation (no pipecat imports needed).
5. **Cache path AND streaming path both honor cancel.** The cache fast-path emits N pre-rendered chunks in a tight for-loop; the streaming path emits chunks as they come off ffmpeg's stdout via an asyncio.Queue. Both have the same fade-out semantics: at each chunk-emit iteration, check _cancel_event.is_set(), fade if set, yield, break. New run_tts calls clear the event so a stale cancel from a prior utterance can't poison the next one — important because cancel_pending is fire-and-forget.
6. **kill_running_action bounded by 1s timeout.** The Claude SDK's kill_running_action might wait on a dead Node.js subprocess. Wrapping it in asyncio.wait_for(..., timeout=1.0) ensures the cancel path can never hang on SDK teardown. Best-effort: timeout/exception logged and swallowed.
7. **End-to-end integration test uses unit-level harness, NOT pipecat.** The PRD explicitly authorizes this fallback. The full pipecat pipeline is mocked via test_pipeline.py's _make_pipecat_modules, but assembling a live-fire integration with the cancel chain through that mock-suite is heavyweight and brittle. Instead, the integration test wires a _SlowBackend (no kill_running_action — verifies the cancel path works without it) plus a real ConversationManager + IntentQueue + ActionWorker, exercising every collaborator on the cancel hot path. The result is a 1.5s budget assertion that mirrors AC#5 (web_fetch cancel within 1s) at the chain level.

### Gotchas
- macOS vs Linux process-group semantics. asyncio.create_subprocess_shell with start_new_session=True works on both via posix_spawn → setsid. os.killpg(os.getpgid(pid), …) is the canonical idiom; os.killpg(pid, …) (passing the leader's PID directly) is wrong on macOS where the PGID may differ from the PID under exotic shells. The implementation uses os.getpgid(proc.pid) explicitly. The orphan-process test runs on the developer's macOS box but the same code path runs on Linux CI.
- The first call to cancel_pending() before any run_tts() invocation finds _live_proc=None and _cancel_dropped=0. Idempotent: returns 0, sets the event harmlessly. The next run_tts() clears the event before yielding any frames, so the stale set doesn't suppress real audio.

In production, the generator's submission path records pending automatically; the test bypasses the generator (uses raw IntentQueue.submit) and so must populate the row manually.
