# Що голос знає про здатності (план, 02.11)

Рішення власника: чітко, уніфіковано, без дублювання, у межах поточної
архітектури. Контекст голосу не засмічується. Фіксимо ізольовано.

## Що вже є (нового реєстру НЕ робимо)

| Потреба | Уже є | Де |
|---|---|---|
| Одна форма здатності | скіл: `name`, `about`, `params`, `effect` | протокол §6, `heare-brain/heare/api/skills.py` |
| Реєстр | скіли в записі частини | `api/registry.py`, `GET /api/skills` |
| Каталог у кожному ході | блок «My body», до 1000 символів | `prompt/body.py` |
| Перелік рук | `about` у `delegate` | `tools/schemas.py::delegate` |
| Чесне «не вмію» | правило в персоні | `prompt/persona.py`, блок про тіло |
| Руки бачать скіли | `catalog()` → `part__skill` | `native_hands.py` |
| Передача далі | `Handoff`, відмова без рук | `model/route.py` |

## Де справді діра

1. Здатності рук живуть поза скілами: `at_hand.SCHEMAS`, `go_deep`, `http_request`.
   Голос про них знає лише з одного рядка `about`.
2. `about` рук застарів: немає глибокого режиму й меж.
3. Правило «не вмію» в персоні не перевірене наживо (`voice_eval`).
4. Руки не мають правила швидкої відмови: можуть витратити кроки на «ракету».
5. `pass_to_cli_hands` пропонується, коли інших рук немає.
6. Голос може назвати не того виконавця.

## Кроки (кожен окремий коміт, окрема перевірка)

### Крок 1. Сторож: `voice_eval` на здатності
Спершу виміряти, потім міняти. Нові випадки в `tests/heare/evals/voice_cases.jsonl`:
«запусти ракету» (не `delegate`, чесна відмова), «увімкни лампу», «порахуй файли
в Downloads» (`delegate`), «що в мене на екрані». Записати результат до змін.

### Крок 2. Руки приносять здатності як скіли
- `at_hand`: схеми стають записами форми §6 із чесним `effect`.
- Стук `native_hands` несе їх у `skills`; `checked()` не змінюється.
- Захист: скіли виконавця йдуть лише через руки. `tools/bodies.py` і `toolbox`
  не дають `read_body` їх викликати, бо інакше голос читав би файли повз руки.
- `catalog()` не бере власні скіли рук, щоб вони не викликали себе через мозок.
- `prompt/body.py`: у виконавця всі скіли під «through the hands».
- Зміна скілів змінює довіру: частина буде перепитана один раз.
Тести: read_body відмовляє на скіл рук; catalog без себе; блок показує руки.

### Крок 3. Каталог лишається малим
- Міряти `make prompt`: блок має вкладатись у `MAX_CHARS`.
- Скіли рук стисло, одним реченням на групу (`_does`).
- `about` рук: що вміють, чого ні, скільки триває; без дублю зі скілами.

### Крок 4. Правило в персоні
Уточнити наявне, не додавати нове: немає в каталозі — скажи, що не вмієш;
«спробую» замість «зроблю». Перевірка: крок 1.

### Крок 5. Руки відмовляють швидко
`_SYSTEM`: немає інструмента — одразу сказати чому, без `go_deep`.
Тест зі сценарієм; жива «ракета» через `delegate`.

### Крок 6. Передача лише коли є кому
`NativeHand` не пропонує `pass_to_cli_hands`, коли `GET /api/skills` не показує
інших виконавців. Відмова в `route.py` лишається страховкою.

### Крок 7. Чесний виконавець
Результат справи несе ім'я рук з `Task.executor`; голос каже лише його.
Тест на текст результату і випадок у `voice_eval`.

### Крок 8. Вибір інструментів для рук
Швидкий режим: скіли частин і читання. Глибокий: решта. Менше схем для дешевої
моделі. Перевірка: `make bench`, `make eval-route`.

## Не робимо зараз

`find_ability` і прогресивне розкриття. Повернемось, коли каталог не вміститься в
`MAX_CHARS` або здатностей стане понад 50. Форма скіла це дозволить без змін
протоколу: `GET /api/skills` уже віддає повний опис.

## Порядок випуску

Кроки 1, 3, 4, 5, 6, 7, 8 не змінюють протокол. Крок 2 розширює дані стуку, але
не форму: мозок спершу, потім мак. Кожна зміна коду рук просить «Дозволити».

## Готово, коли

- `voice_eval`: усі випадки з кроку 1 проходять тричі поспіль.
- «Запусти ракету» голосом: чесна відмова без передачі.
- «Порахуй файли»: реальне число від правильних рук.
- Блок «My body» не зростає понад `MAX_CHARS`.
